# Rubberr Agent Platform — Runbook (Phase 2)

**Status:** Phase 2 integration complete on paper + unit/integration tests. **No
real relay/companion/browser E2E has been run** — that is Phase 4, owner-in-the-loop,
requires Y6 access. See "What Phase 4 must still verify" at the bottom.

This is the one document that says, per host, exactly what to run and in what
order to bring up the whole platform: Y6 (relay + Tier-2 feed + public
companion), the user's own machine (their companion + their Chrome),
and Cloudflare Pages (frontend).

---

## 0. The four hosts

| Host | Runs | Why |
|---|---|---|
| **Y6** (Windows, Tailscale) | relay server, Tier-2 feed (scraper_job + api), the **public** companion (for Tier-1 USATT lookups), the backend (`rubberr/backend/main.py`) | always-on, has Tailscale/owner access |
| **User's machine** (Mac/Win) | their own **companion** + their own already-logged-in Chrome | Tier-3 private sync needs the user's own session; nothing about their login ever leaves their machine |
| **Cloudflare Pages** | `rubberr/frontend/` | static/edge hosting for the Next.js app |
| **Cloudflare** (in front of Y6) | TLS termination + routing to relay/backend/feed | per build plan §"Hosting" |

## 0.1 Owner-only posture (final hardening pass, S1/S2-profile/S3)

This platform is deliberately **owner-only and self-hosted** — one operator
(you), never a multi-tenant account system. That decision shapes three
concrete gates, all closed by default:

- **The relay is not publicly exposed as an open control plane.** Cloudflare
  sits in front of it for TLS, but its control endpoints
  (`/session/start`, `/session/stop`, `/session/gate`) additionally require an
  `X-Operator-Token` header matching `RELAY_OPERATOR_TOKEN` (`relay/config.py`,
  enforced by `relay/server.py`'s `_require_operator_token`). If
  `RELAY_OPERATOR_TOKEN` is unset, those endpoints refuse with a `503` —
  they never silently run open. `/session/start` also only ever mints a
  session from a **server-validated `register_token`**; a caller-supplied
  `user_id` is never trusted (fixed S3 finding — see `relay/test_relay.py`'s
  `test_session_start_rejects_bare_user_id_without_register_token`).
- **The backend's Tier-3 sync + Tier-1 lookup endpoints are owner-gated
  too**, independently of the relay's own gate: `POST /tools/sync/stadium`,
  `GET /tools/sync/stadium/events/{id}`, `POST /tools/sync/omnipong`,
  `GET /tools/sync/omnipong/events/{id}`, and `GET /tools/lookup/usatt` all
  require `X-Operator-Token` matching `OPERATOR_TOKEN` (`rubberr/backend/main.py`'s
  `_require_operator_token`). Same fail-closed rule: unset `OPERATOR_TOKEN` on
  the backend means a clean `503`, never an open endpoint. The owner's own
  frontend sends this header automatically (`DemoBar.tsx`'s `getAIHeaders()`,
  fed by `NEXT_PUBLIC_OPERATOR_TOKEN` — see `rubberr/frontend/.env.local.example`).
  `OPERATOR_TOKEN` (backend) and `RELAY_OPERATOR_TOKEN` (relay) are
  **independent secrets** gating two different control planes — set both,
  they don't have to be the same value, but the backend's calls into the
  relay (`_provision_relay_session`, `_stop_relay_session`, and
  `browser_agent.py`'s `RelayGateClient.open_gate`) all forward
  `RELAY_OPERATOR_TOKEN` on the backend's behalf.
- **The agent only ever drives a DEDICATED Chrome profile**, never the
  owner's everyday Chrome. `companion/chrome.py`'s `dedicated_profile_dir()`
  points `--user-data-dir` at a rubberr-only profile directory (override via
  `RUBBERR_CHROME_PROFILE_DIR`) — see `companion/README.md`'s "The dedicated
  Chrome profile" section for the one-time login flow. Because it's a
  separate profile directory, the companion no longer needs to ask you to
  quit your regular Chrome first; the two run as fully independent processes.

Where the secrets live: `RELAY_OPERATOR_TOKEN` and `OPERATOR_TOKEN` go in the
root `.env` (see `.env.example`); register tokens stay in the gitignored
`relay/register_tokens.json` (§1 below); the frontend's copy of the operator
token goes in `rubberr/frontend/.env.local` as `NEXT_PUBLIC_OPERATOR_TOKEN`
(a build-time constant is acceptable ONLY because this is a single-owner,
self-hosted deployment — it ships in the client bundle).

## 1. One-time setup (any host, before first run)

```bash
cd ~/Desktop/omnipong
cp .env.example .env
# fill in: RELAY_BASE_URL, RELAY_REGISTER_TOKEN, RELAY_PUBLIC_REGISTER_TOKEN,
#          RELAY_OPERATOR_TOKEN, OPERATOR_TOKEN, OMNIPONG_USER/PASS,
#          ANTHROPIC_API_KEY, etc. — see .env.example's comments for exactly
#          which var is read by which component, and §0.1 above for the two
#          operator-token gates specifically.
```

Register tokens are **not** generated by any script — they're opaque strings
you choose and add to `relay/register_tokens.json` (gitignored):

```json
{
  "rt_owner_abc123": "u_owner",
  "rt_public_def456": "u_public_lookup"
}
```

Put the matching value of `rt_owner_abc123` into `.env`'s `RELAY_REGISTER_TOKEN`
(so the backend can start Tier-3 sessions) and pass it to your own companion's
`--register-token` flag. Put `rt_public_def456` into `RELAY_PUBLIC_REGISTER_TOKEN`
and use it for the Y6 public companion (§4).

## 4. Y6 — the public companion (Tier-1 USATT lookup)

This is the "shared always-on companion+browser" `RELAY_PUBLIC_REGISTER_TOKEN`
resolves to (seam #4). It is a **normal companion instance**, nothing special
in the code — just: (a) run on Y6 instead of a user's machine, (b) registered
with the `rt_public_...` token, (c) never asked to log into anything (USATT is
looked up logged-out; Cloudflare-walled, not login-walled).

```bash
cd ~/Desktop/omnipong/companion
python companion.py \
  --relay-base-url wss://relay.rubberr.<domain> \
  --register-token rt_public_def456 \
  --chrome-port 9223           # distinct port from any other companion on the box
```

Leave this running. The backend calls relay `POST /session/start` with
`RELAY_PUBLIC_REGISTER_TOKEN` fresh **on every** `/tools/lookup/usatt` call
(sessions have a `RELAY_MAX_TTL_S` cap — 15 min by default — so there is no
long-lived static session to keep alive; see `main.py: _provision_relay_session`).
If this companion isn't running, lookups fail with a clean 503 (`No public
relay companion configured` / relay's `CompanionNotOnline`) — never fake data.

## 8. End-to-end order for a Tier-3 private sync (what actually has to be running)

1. Y6: relay (§2) up.
2. Y6: backend (§5) up, `RELAY_BASE_URL`/`RELAY_REGISTER_TOKEN` set.
3. User's machine: companion (§6) running, registered with the SAME
   `RELAY_REGISTER_TOKEN` value the backend has.
4. User is logged into Stadium in the Chrome window the companion opened.
5. User opens the frontend (§7), adds their OpenRouter key (top bar BYOK
   modal), clicks "Sync my Stadium data" on `/scoreboard` (or wherever
   `StadiumSyncPanel` is mounted).
6. `POST /tools/sync/stadium {player_name}` -> backend calls relay
   `POST /session/start {register_token}` -> mints a `session_token` -> backend
   starts `run_browser_task(...)` in the background and returns
   `{"session_id": <that session_token>}` immediately.
7. Frontend opens `GET /tools/sync/stadium/events?session_id=...` (SSE).
   Backend streams `gate_open` -> user solves it in their own Chrome tab and
   clicks "Continue" in the companion's gate UI -> `gate_cleared` -> ... ->
   `done` with the final `BrowserTaskResult`.
8. Frontend saves `matches[]` to the browser's own IndexedDB ledger
   (`lib/ledger.ts`) — nothing private is written server-side.

For a Tier-1 lookup: just §2 (relay) + §4 (public companion) + §5 (backend) +
§7 (frontend) need to be up — no companion on the user's machine required.

## 10. What Phase 4 (owner-in-the-loop) must still verify — NOT done here

Per the workspace's own rule (unit tests are not proof) and the task's
explicit scope ("Do NOT run a real browser/relay/login E2E — that's Phase 4"),
none of the following has been exercised for real in Phase 2:

1. **Y6 up, real relay + real companion + real Chrome.** The relay/companion
   wire protocol is verified against each other's own test suites
   (`relay/test_relay.py`, `companion/selfcheck.py`) with a **mock** peer on
   each side — never against each other, live, over a real network.
2. **A real login.** Log into Stadium (or USATT) for real, let the agent hit
   an actual Cloudflare/login gate, confirm the pause genuinely holds (per
   `browser_agent.py`'s blocking-in-hook design, informed by
   `docs/BROWSER_USE_SPIKE.md`'s OQ-3 finding that `pause()` alone does not
   stop the triggering step) and that clicking "Continue" in the companion's
   gate UI actually resumes the scrape.
3. **A real scrape returning real matches**, through the full relay tunnel,
   landing in the frontend's IndexedDB ledger via the SSE bridge documented
   in §8 above (which Phase 2 verified only with a **mocked**
   `run_browser_task` — see `rubberr/backend/tests/test_sync_sse_integration.py`).
4. **Timing/cost measurements** the build plan's Phase 4 asks for:
   time-to-first-scrape, OpenRouter token cost, gate-handoff latency.
5. **The public companion (§4) actually clearing a real Cloudflare challenge**
   on usatt.simplycompete.com logged out.
6. **The dedicated Chrome profile's one-time login, for real** (§0.1 /
   `companion/README.md`): launching a genuinely fresh
   `dedicated_profile_dir()`, logging into Stadium once by hand, quitting and
   relaunching the companion, and confirming the session persists — this
   pass only verified the code path (profile dir resolution, `--user-data-dir`
   wiring) and the existing mock-relay/mock-Chrome self-check, not a real
   Chrome launch against a real dedicated profile.
7. **The operator-token gates end-to-end against a real deployed relay +
   backend** (§0.1) — this pass proved the gate logic in-process
   (`relay/test_relay.py`, `rubberr/backend/tests/test_operator_gate.py`),
   not that Cloudflare/production config actually delivers the
   `X-Operator-Token` header unmolested, or that a real anonymous request
   from the open internet gets the same 401/503 a local test client sees.

Everything above needs Y6 access + a real OpenRouter key + a real Stadium/USATT
login, none of which this Phase 2 pass had.
